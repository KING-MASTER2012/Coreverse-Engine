## What happened compared to the previous commit? (platform Phase 9: input)
- added (platform): new module `platform::input` (`input/{button,key,pointer,ime,event,state}.rs`): `InputEvent` (`Key`, `ModifiersChanged`, `CursorMoved`, `CursorEntered`, `CursorLeft`, `MouseButton`, `MouseWheel`, `RawMouseMotion`, `Touch`, `Ime`), `KeyEvent` with the physical `KeyCode` (W3C `code` names, 132 keys) and the logical `Key` (`Named(NamedKey)`, `Character`, `Dead`, `Unidentified`) plus text, `repeat` and `synthetic`, `Modifiers`, `MouseButton`, `ButtonState`, `ScrollDelta` (lines or pixels), `PointerPosition` (fractional physical pixels), `TouchEvent`/`TouchPhase`/`TouchPoint`, `ImeEvent` (`Enabled`, `Preedit`, `Commit`, `Disabled`). All enums are `#[non_exhaustive]`; no new dependency.
- added (query layer): `InputState`, the per-frame layer on top of the events: `key_pressed`/`key_just_pressed`/`key_just_released` (physical), `logical_key_*`, `mouse_*`, `cursor_position` (`None` outside the window) and `cursor_delta`, `raw_mouse_delta`, `scroll_lines`/`scroll_pixels`, `touches*`, `text` (printable characters typed this frame plus IME commits) and `ime_preedit`; `handle_event`/`handle_input`, `end_frame`, `release_all`. Auto-repeat is not a new press; a press and release inside one frame reports both; losing focus releases everything; a cursor position from before it left the window gives no jump. One `InputState` per window.
- added (window API): `WindowEvent::Input(InputEvent)` (the one new variant; `WindowEvent` was already `#[non_exhaustive]`), `HostEvent::Input { window, event }` for the headless backend (IME events are dropped while the window does not allow IME, everything else is delivered as given), `AppContext::set_ime_allowed` and `set_ime_cursor_area` (position and size in logical units; invalid values give `WindowError::InvalidArgument`), `Window::is_ime_allowed` (off for new windows, reads back at once).
- added (desktop backend): the `winit` events `KeyboardInput`, `ModifiersChanged`, `CursorMoved/Entered/Left`, `MouseInput`, `MouseWheel`, `Touch` and `Ime` are converted (`window/winit_input.rs`) and delivered; raw mouse motion (`DeviceEvent::MouseMotion`) is delivered to the focused window (lowest id if several); IME permission and caret area are passed to `winit`. Keys or named keys without a counterpart become `KeyCode::Unidentified` / `Key::Unidentified`.
- added (tests): 34 unit tests in `input/*` and 2 doc tests (an `App` that queries an `InputState`, and the `InputState` example), 5 conversion tests in `winit_input.rs`, 3 headless tests in `window/tests.rs` (input order per window, IME dropped until allowed, an `App` asking an `InputState` per frame through the event stream including a focus loss), 2 in `window/app.rs` (IME permission reads back / invalid caret area rejected), and the Xvfb smoke test now also switches IME on and sets the caret area.
- changed: `window/{event,app,state,headless,mod,winit_backend}.rs`, `lib.rs`, `tests/winit_smoke.rs`, `docs/src/platform.md` (new "Input" section, modules and verification tables), README and the introduction. No change to `ffi`, `cv-ffi` or CI.

## What happened compared to the previous commit? (platform Phase 7: window API and headless backend)
- added (platform): `platform::window` (`engine/rust/crates/platform/src/window/`), the engine-owned window API. `App` (callbacks `resumed`, `suspended`, `window_event`, `about_to_wait`; the lifecycle and its ordering are documented on the trait and in `docs/src/platform.md`), `AppContext` (create/close windows, title, visibility, size, position, fullscreen, `request_redraw`, `ControlFlow`, `exit`), `Window` (readable state), `WindowDesc` (builder + `validate`), `WindowEvent` (`CloseRequested`, `Destroyed`, `Resized`, `Moved`, `ScaleFactorChanged`, `Focused`, `Occluded`, `RedrawRequested`, `SurfaceCreated`, `SurfaceLost`; `#[non_exhaustive]`, input events come later), `WindowId`, logical/physical size and position types, `WindowError` (convertible into `CoreError`), and the `Backend` trait.
- added (platform): `NativeWindowHandle`, one variant per windowing system and mirroring `DisplayServer`: `Win32`, `Cocoa`, `X11`, `Wayland`, `Android`, `UiKit`. The fields are what the C++ `renderer::NativeWindowHandle` takes today plus `ANativeWindow*` (Android) and `CAMetalLayer*` (iOS). Pointers are non-zero integers, so the type is `Copy + Send + Sync` and the crate stays free of `unsafe`.
- added (platform): the headless backend: `HeadlessLoop` (step-by-step, hands the app back for inspection), `HeadlessBackend` (implements `Backend::run`), `HeadlessConfig` (scale factor, monitor size) and `HostEvent` (what a test plays as the operating system: close click, resize, move, scale-factor change, focus, occlusion, `Suspend`/`Resume`, `SurfaceCreated`/`SurfaceLost`). Requests such as a resize or fullscreen come back as events the way a window manager would send them. No clock: `WaitUntil` behaves like `Wait`; a loop that waits with nothing queued is idle (`Backend::run` reports `WindowError::Stalled`); a loop that produces events forever stops with `EventStorm`.
- design decisions: the API lives in the `platform` crate (as `platform::window`, matching the planned `ffi_platform_run`), not in a new crate; the desktop backend will be an optional dependency so the crate stays light without it. Windows are created in `resumed`. Surfaces are explicit events (`SurfaceCreated`/`SurfaceLost`), and every created surface is lost exactly once, before `suspended` and before `Destroyed`. Title and visibility are app-owned and read back at once; size, position and fullscreen are requests answered by events. `ControlFlow` is `Poll`/`Wait`/`WaitUntil`. Not designed yet, on purpose: monitors, cursor, input events, exclusive fullscreen, FFI (Phase 10).
- changed: `platform` crate docs list the new module and say `unsupported` instead of `none` in the support table; `docs/src/platform.md` has a new section (lifecycle contract, handle table, backends), README and the introduction mention the window API.
- tests (Phase 7): 67 new unit tests and 3 doc tests in `platform` (geometry, handle mapping, `WindowDesc` validation, `AppContext` requests, and 30+ behavior tests of the headless loop: start-up and idleness, close/destroy order, surface replacement and loss, suspend/resume ordering, redraw timing, resize/move/fullscreen requests, scale-factor changes, exit and the `Backend` contract). A mutation (calling `suspended` before the surface loss) made two of them fail and was reverted.
- verified (sandbox, Linux x86_64, Rust 1.99.0): `cargo test -p platform --all-features` 157 unit + 5 doc tests green, `cargo test --workspace --all-features` green, `cargo fmt --all --check` and `devkit/scripts/format.sh --check` clean, `cargo clippy -p platform --all-targets -- -D warnings -A deprecated` clean, `RUSTDOCFLAGS="-D warnings" cargo doc -p platform --no-deps` clean, `cargo check -p platform` for `aarch64-linux-android`, `aarch64-apple-ios`, `aarch64-apple-darwin`, `x86_64-pc-windows-msvc` passes (type-check only), `mdbook build` has no warnings. The CI mobile job already covers the new module (nothing in it is platform-specific).
- not verified: running the new tests on Windows or macOS (no code in the module is platform-specific, but only the CI runners can confirm); everything real: no window is opened by anything in this phase.
- known issue (unchanged, not part of this phase): the `fetch_update` deprecation on Rust 1.99 described in the previous entry still breaks `-D warnings` Clippy on a toolchain that new.
- not done on purpose: Phases 8-11 (winit desktop backend, input, runtime/FFI integration, mobile backends) wait for their own design review and "Uygula".

## What happened compared to the previous commit? (Phase 7c, kept for history)
- added (Phase 7c): six new `ffi::vfs` functions matching what `vfs_crate::file_manager` already had: `ffi_vfs_remove`, `ffi_vfs_metadata`, `ffi_vfs_list_dir` (+ `ffi_vfs_free_string_array`), `ffi_vfs_add_file` (covers both `add_file` and `add_file_to` via a nullable `dest_rel`), `ffi_vfs_new_temp_path`. Same thread-local last-error pattern as the existing functions.
- added (Phase 7c): `cv-ffi` (engine/cpp/ffi-cpp) - C++ RAII wrappers over the `ffi` crate's raw C ABI. `cv_ffi::Logger`/`cv_ffi::DiagnosticBuilder` are move-only RAII types (same shape as `renderer::Buffer`/`Swapchain`); `cv_ffi::vfs::*` are `std::expected`-returning free functions wrapping the `ffi_vfs_*` calls (Init/ReadToString/ReadBytes/WriteBytes/Exists/Remove/GetMetadata/ListDir/AddFile/NewTempPath); `cv_ffi::BuildInfoString()` wraps `ffi_build_info_string`. `ffi.h` is only included from `cv-ffi`'s `.cpp` files, never from its public headers. `editor` now links `cv-ffi` instead of calling `link_ffi(editor)` itself.
- fixed while writing the wrappers: `ffi_logger_add_console_sink`/`add_file_sink`/`set_min_severity`/`shutdown` and `ffi_diagnostic_builder_set_*`/`emit` all dereference their `Logger*`/`DiagnosticBuilder*` unconditionally on the Rust side (no null check - confirmed by reading logger.rs/diagnostic.rs). Every `cv_ffi::Logger`/`DiagnosticBuilder` method now guards against being called on an invalid (default-constructed or moved-from) handle before making that call, instead of risking UB. `DiagnosticBuilder::Emit()` specifically checks the target `Logger`'s validity too.
- added (Phase 7c): renderer -> ffi logger bridge, via a callback rather than a direct dependency. `RenderDevice::SetLogCallback(LogCallback)` (renderer/RenderDevice.hpp) is new; `VulkanRenderDevice`'s debug messenger (already existed for `ValidationErrorCount()`) now also forwards every warning/error it sees to that callback, mapped to `RenderDevice::LogSeverity`. `renderer` still has zero dependency on `ffi`/Rust - the mapping into `cv_ffi::Severity` and the actual `DiagnosticBuilder`/`Logger` calls live in `ViewportRenderer::initialize()` (editor-side), under producer `"CV-RENDERER"` / category `"VULKAN"`. `EditorWindow` registers that producer once at startup and owns the `cv_ffi::Logger` (console sink; a file sink needs a project root this editor doesn't have yet - see below) that both its own diagnostics and the renderer's now go through. `ViewportRenderer::shutdown()` clears the callback before the device goes away.
- decided (Phase 7c): `VfsContext` re-init - no code change. `VfsContext::init`/`init_with_fs` stay a genuine once-per-process `OnceLock`; a safe reset would need either `unsafe` code overwriting a shared `static` behind other threads' backs, or an `RwLock`/`Option` layer every `VfsContext::global()` call would pay for, for a caller (switching projects without restarting) that doesn't exist yet. Documented on `VfsContext`'s doc comment. The practical consequence - each of this crate's tests that calls `init_with_fs` needs its own file under `tests/` (its own process) - is now spelled out there too; `tests/list_dir_and_metadata.rs` (new) follows it.
- added: `tests/list_dir_and_metadata.rs` (vfs crate) covering `list_dir`/`metadata`/`remove`/`add_file`/`add_file_to`/`new_temp_path` at the `file_manager` level - the same calls the new `ffi_vfs_*` functions forward to.
- note: the Rust side of this phase (`ffi/src/vfs.rs`, `vfs/src/context.rs`, the new `vfs` test) was hand-written and carefully re-read, not compiled - the sandbox this was built in only has rustc 1.75 (apt), and this workspace's `edition = "2024"` needs 1.85+, with no path to a newer toolchain available there (no network access to static.rust-lang.org for rustup). ## What happened compared to the previous commit? (Phase 6.4, superseded by the entry above but kept for history)
- added (Phase 6.4): `renderer::FrameSync` (renderer/FrameSync.hpp) - the frame-level synchronization abstraction. `RenderDevice::CreateFrameSync()` builds it; `BeginFrame(swapchain)` waits for the in-flight slot's previous frame, acquires an image (100 ms timeout, so a hidden window can never block the GUI thread) and hands out a reset command buffer; `EndFrame(swapchain, frame)` submits and presents. Semaphores/fences stay inside the backend (acquire semaphore + fence + command buffer per in-flight slot, render-finished semaphore per swapchain image); a rebuilt swapchain is noticed by the next `BeginFrame()`, no extra call. Vulkan implementation in VulkanRenderDevice.cpp; `framesInFlight` is clamped to [1, 8].
- added (Phase 6.4): the editor render loop. `ViewportRenderer` owns a `FrameSync` (after the swapchain, so it dies first) and renders from a ~60 Hz timer on the GUI thread: a clear to a slowly cycling color, FPS in the status bar. The loop rests while the viewport is hidden or the window is minimized, and while the swapchain cannot be rebuilt yet (zero-sized viewport, failed rebuild - retried on the next resize and every 250 ms). `rebuildSwapchain(force)` no longer skips a rebuild just because the size is unchanged, so `OutOfDate` is always handled. Fatal errors (device lost, failed submit/present) stop rendering and show up in the status bar; recovering from them is not implemented.
- added: `Swapchain::Acquire(semaphore, timeoutNs)` and `SwapchainStatus::NotReady` (timeout expired, nothing acquired). `VK_ERROR_DEVICE_LOST` / `VK_ERROR_OUT_OF_*_MEMORY` now map to `RenderErrorCode::DeviceLost` / `OutOfMemory` for acquire, present, submit and begin/end instead of `Unknown`.
- added: validation as a test signal. `renderer::ValidationErrorCount()` (renderer/Diagnostics.hpp) counts validation-layer errors, `RenderDevice::IsValidationEnabled()` says whether the layer is running, `RENDERER_FORCE_VALIDATION` (CMake option) enables the layer in every build type. Linux CI installs `vulkan-validationlayers`, configures with the option and sets `CV_REQUIRE_VALIDATION=1`, which makes the tests fail if the layer is not actually running.
- added: `frame_sync_test` (gpu): 1, 2 and more-frames-than-images in flight, ~140 frames each with a resize in the middle, Acquire timeout, misuse checks, move semantics, zero validation errors. `editor --smoke-frames N` + ctest `editor_render_smoke` (labels `gpu;editor`): the real Qt window renders N frames, is resized half-way, quits by itself and must find no validation errors. CI runs it in its own step; it was non-blocking while the vcpkg Qt xcb plugin was unverified and is a regular gate now (see the P0 entry above).
- note: `AcquireCommandBuffer()` allocates a new command buffer on every call and only frees them at `Shutdown()` - use it once per long-lived buffer; per-frame buffers come from `FrameSync`. Documented on the function.
- note: `Submit()` still waits at the TRANSFER stage (right for a clear). The first real graphics pass must change it to COLOR_ATTACHMENT_OUTPUT (comment in `VulkanRenderDevice::Submit`).
- note: nothing is drawn in the viewport except the clear color yet.
