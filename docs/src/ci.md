# Continuous integration

Workflows live in `.github/workflows/`; `ci.yml` is the entry point. On a pull request it runs only the parts the changed files need (see *Path filters and `ci-ok`* below) and ends in the single check `ci-ok`.

| Workflow                                                | What it does                                                                                                                                                                                                                                                                                                                     |
|:--------------------------------------------------------|:---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `rust.yml`                                              | Cargo test on Linux (plus the `no_std` math backend) and on Windows/macOS; `cargo check` and Clippy of `platform` for Android and iOS; a window smoke test on Xvfb. The mobile and window-system jobs only run when `ffi` or its dependencies changed                                                                            |
| `changes.yml`                                           | Decides from the changed files which jobs a pull request needs (`.github/ci-areas.txt`, `.github/scripts/changed-areas.py`)                                                                                                                                                                                                      |
| `cpp.yml`                                               | C++/Qt builds and tests on Linux (in the toolchain image: GCC, Xvfb, software Vulkan with validation, Wayland test), Windows (MSVC) and macOS (Apple Clang)                                                                                                                                                                      |
| `image.yml`                                             | Makes sure the Linux toolchain image for this revision exists: a lookup, or a build and push when the Dockerfile or the minimum tool versions changed                                                                                                                                                                            |
| `lint.yml`                                              | Clippy with `-D warnings`, Rustdoc                                                                                                                                                                                                                                                                                               |
| `formatting.yml`                                        | `cargo fmt --check`, clang-format over C++ and Objective-C++                                                                                                                                                                                                                                                                     |
| `cache-warm.yml`                                        | Nightly run of `cpp.yml` on the default branch: keeps the vcpkg binary cache from expiring and refreshes it after a runner image update                                                                                                                                                                                          |

| `nightly.yml`, `release.yml`, `deploy.yml`, `stale.yml` | Scheduled / release automation                                                                                                                                                                                                                                                                                                   |

The CMake minimum, the Rust toolchain and LLVM versions come from `devkit/scripts/setup/config/tool-versions.json`.

## vcpkg: pinned version and binary cache

* **The vcpkg version is the submodule commit.** `third_party/vcpkg` is a git submodule and the commit this repository points to is the vcpkg that every machine and every CI job uses (the Linux/macOS bootstrap, the Windows bootstrap and the macOS CI job follow the same rule; nothing runs `git pull` any more). To move to another version: `git -C third_party/vcpkg fetch origin`, `git -C third_party/vcpkg checkout <commit>`, `git add third_party/vcpkg`, commit. `builtin-baseline` in `vcpkg.json` is separate: it pins the *port* versions (Qt, Vulkan headers, ...). The submodule is not fetched shallow on purpose: vcpkg reads the baseline commit from its own history.
* **Binary cache.** Building Qt from source is what made the C++ jobs slow. `.github/actions/vcpkg-cache` restores a directory of per-package archives before the packages are installed and points vcpkg at it (`VCPKG_BINARY_SOURCES`). The cache key contains the OS and architecture, the compiler, the pinned vcpkg commit, the dependency part of `vcpkg.json` and the target triplets of the presets, so a hit always holds binaries vcpkg would accept.
* **Who writes it.** Only runs on the default branch save the cache (`actions/cache/save` right after the packages are installed). Pull requests only restore it, so they cannot fill the repository's cache quota. `codeql.yml` restores it too.
* **Keeping it alive.** GitHub deletes cache entries that were not used for 7 days, and a runner image update that changes the compiler changes the key. `cache-warm.yml` runs the C++ pipeline every night on the default branch for both reasons. A pull request opened right after an image update, before the next nightly run, builds the packages once itself.
* **Resetting it.** Change the `revision` input of the action (default `1`) to discard every entry.

## Toolchain image (Linux C++ jobs)

* **What it is.** `devkit/ci/image/Dockerfile` builds `ghcr.io/<owner>/coreverse-ci:<hash>`: GCC, ccache, CMake, Ninja, Rust, cbindgen, the Qt xcb build libraries and the X11/Wayland/software-Vulkan test stack. The Linux C++ job (`cpp.yml`) and the C++ CodeQL analysis run inside it, so they no longer run Bootstrap or `apt-get`. Bootstrap is a developer tool. LLVM, clang-tidy, LLDB, GDB, cppcheck and mdBook are not in the image (the CI does not use them), nor are vcpkg and its packages (pinned submodule and binary cache, see above).
* **Who builds it.** `image.yml` runs first in `ci.yml`, `codeql.yml` and `cache-warm.yml`. The tag is a hash of the Dockerfile and of the minimum versions of cargo, CMake, Ninja, cbindgen and GCC in `devkit/scripts/setup/config/tool-versions.json`. If that image is already published the job is a lookup of a few seconds; if not, it builds and pushes it first. A pull request that changes the Dockerfile or those minimum versions therefore builds and tests with its own image, and nothing else has to be edited.
* **Frozen on purpose.** CMake, Ninja, Rust (stable) and cbindgen are whatever was newest when the image was built, like the Bootstrap run they replace, and then stay the same until the image is rebuilt: change `CI_IMAGE_REVISION` in the Dockerfile (or a minimum version) to refresh. The `Toolchain image` step of the Linux job prints the versions. The build fails if a tool is older than its minimum in `tool-versions.json`.
* **Forks and Dependabot.** Their token is read-only, so they cannot publish. They pull the image like everyone else; only a fork pull request that changes the Dockerfile or the minimum versions stops with a message (push the branch to the main repository instead).
* **Package visibility.** The package has to be public (Packages, `coreverse-ci`, package settings) so fork pull requests can pull it. It is named after the repository owner: after a transfer to another account or organization the first run publishes it under the new owner by itself.
* **Windows and macOS** keep their own provisioning: GitHub-hosted Windows and macOS runners cannot run job containers.

## Compiler cache and Cargo cache (C++ jobs)

* **Compiler cache.** `.github/actions/compiler-cache` restores a ccache directory (Linux, macOS) or an sccache directory (Windows: sccache is the one that supports MSVC; version 0.10.0, pinned and checked against its SHA-256) and sets `COREVERSE_COMPILER_LAUNCHER`, which `cmake/Ccache.cmake` reads. In CI the tool is chosen explicitly, so a missing tool fails the configure instead of silently compiling without a cache. ccache hashes the compiler binary (`CCACHE_COMPILERCHECK=content`) and treats paths below the workspace as relative, so entries do not depend on the image or on where the repository is checked out. Each directory is limited to 300 MB.
* **Cargo cache.** `Swatinem/rust-cache` caches the cargo registry and the target directory that Corrosion builds the Rust `ffi` crate in (`build/<preset>/cargo/build`). `lint.yml` and `nightly.yml` use it too. Check the first run's log: the cache size it reports for that directory should not be empty, otherwise the path is wrong.
* **Who writes it.** The same rule as for the vcpkg cache: restored on every run, saved only on the default branch (`actions/cache/save` after the build, also when a test failed). There is one entry per OS, architecture, tool and *day*: the first default-branch run of a day (normally `cache-warm.yml`) saves it, later runs and pull requests restore the newest one. Entries that are not used for a week are deleted by GitHub.
* **CodeQL never uses it.** CodeQL's C++ analysis has to see every compiler run, and a compile that is a cache hit would be missing from the analysis, so that job sets `COREVERSE_COMPILER_LAUNCHER=none`.
* **For developers.** `COREVERSE_COMPILER_LAUNCHER` is `auto` by default (sccache, else ccache, else none, as before) and can be set to `ccache`, `sccache` or `none` as a cache variable or an environment variable. A launcher that is set explicitly (`-DCMAKE_CXX_COMPILER_LAUNCHER=...`) is never overridden.
* **Resetting.** Change the `revision` input of the action (default `1`) to discard every entry.

## Path filters and `ci-ok`

* **What is filtered.** Only pull requests. A push to `main`/`develop`, the nightly run, `cache-warm.yml` and manual runs always run everything. `changes.yml` looks at the files the pull request changes and sets four flags: `rust` (cargo test, Clippy, rustdoc, cross-platform tests, the Rust CodeQL analysis), `cpp` (C++ on three OSes and the toolchain image), `format` (rustfmt/clang-format) and `ffi` (the mobile and window-system jobs of `rust.yml`).
* **The rules** are in `.github/ci-areas.txt`: one `<kind> <glob>` per line (`*` also matches `/`), with comments. `ignore` needs no CI (documentation, `assets/`, repository metadata, workflows that are not part of `ci.yml`), `all` runs everything (the CI itself: `.github/workflows`, `.github/actions`, `.github/scripts`, the rules file). A changed file may match several kinds.
* **What is not in the rules file.** The crates the `ffi` crate depends on. They are worked out from the `Cargo.toml` files on every run (`ffi`, `ccore`, `platform`, `vfs`, `fs`, `log-*`, `root`, `vfs-macros` today), so a Rust change in one of them runs the C++ build and a change in, say, `math` does not, and adding a dependency to `ffi` needs no edit. The job summary of `changes` shows the flags, the first files that caused each one and the computed list.
* **A gap can only cost time.** A changed file that matches no rule at all (a new top-level directory, an unknown file) makes everything run, and so does a failure to list the changed files. Add a rule when the summary of `changes` lists such a file.
* **Why `if:` and not `paths:`.** A workflow skipped by `paths:` never reports its checks, and a *required* check that never reports blocks the pull request forever. For the same reason the checks of jobs inside a reusable workflow that is skipped (`cpp / linux`, `build / rust`, ...) do not exist on a pull request that does not need them. `ci.yml` therefore ends in the job `ci-ok`, which succeeds when every job before it succeeded or was skipped and fails when one failed or was cancelled.
* **Branch protection / ruleset: require `ci-ok` and nothing else from `ci.yml`.** Remove the individual checks (`build / rust`, `cpp / linux`, `cpp / windows`, `cpp / macos`, `lint / lint`, `format / formatting`, ...) from the required list, otherwise a pull request that skips them waits forever. The CodeQL checks are separate workflows and are skipped the same way when their area is skipped; do not require `Analyze (cpp)` (it does not run on pull requests at all) and require `Analyze (rust)` only if a skipped check is acceptable.

## Rust profile in pull requests

* **What.** `[profile.release]` in `Cargo.toml` is fat LTO with one codegen unit. Corrosion builds the Rust `ffi` crate (and everything in its closure, winit included) with it for every C++ Release build, and fat LTO re-optimizes the whole staticlib whenever any of it changes, which is slow and cannot be cached. For pull requests `cpp.yml` (input `fast-rust`, set by `ci.yml`) overrides two settings through the environment (`CARGO_PROFILE_RELEASE_LTO=off`, `CARGO_PROFILE_RELEASE_CODEGEN_UNITS=16`). It is still the release profile (optimized, `opt-level` unchanged), only without LTO.
* **What stays full.** Pushes to `main`/`develop` build the unchanged release profile, so a release-only problem is found there, not in the pull request. `release.yml` is unchanged. The `cargo test` jobs of `rust.yml` use the dev profile and are not affected.
* **Cargo cache per profile.** The cache key of the Rust cache carries the profile (`fast-rust` or `full-lto`). `cache-warm.yml` builds the `fast-rust` variant every night on the default branch, which is what pull requests restore; pushes to the default branch save the `full-lto` variant for themselves.
* **No `[profile.ci]` in `Cargo.toml`.** A separate profile would have to be selected through Corrosion (`PROFILE`), which depends on the Corrosion version; overriding the release profile through the environment works with any.

## Bootstrap smoke test

`bootstrap-smoke.yml` is not part of `ci.yml` and not a required check, so it uses `paths:`. On a pull request that changes `devkit/scripts/setup` it checks that every shell script (`bash -n`) and PowerShell script (the PowerShell parser) still parses and that `bootstrap.sh --dry-run` still walks through its task graph. Weekly (Monday 04:41 UTC) and on demand it runs a real Bootstrap on a bare Ubuntu runner after installing the Qt xcb packages a developer needs first, restores (never saves) the vcpkg cache and then checks that cmake, ninja, cargo, cbindgen, vcpkg and `vcpkg_installed` exist. The Windows Bootstrap is exercised by `cpp.yml` on every C++ change. macOS is not covered: `bootstrap.sh` does not run on macOS's default bash 3.2 yet.

## No vcpkg asset cache

vcpkg can also cache the source archives it downloads (`X_VCPKG_ASSET_SOURCES`, or the `downloads` directory). It is not used: the binary cache means sources are only downloaded on a miss (a new compiler, a changed manifest), which the nightly run absorbs, and a cache of Qt's sources would take a large share of the repository's cache quota. Revisit it if downloads start failing on cold runs.
